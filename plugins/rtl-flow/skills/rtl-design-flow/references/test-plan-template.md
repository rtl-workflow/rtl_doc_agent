## 二、测试用例列表（Test Case）

> 字段说明：
> - **测试用例编号**：用例唯一编号，命名规范 `tc_<对象>_<场景>_<序号>`
> - **所覆盖测试点编号**：本用例覆盖的测试点编号（可多选，换行分隔）
> - **测试用例标题**：用例简要描述
> - **TC 描述**：用例详细执行步骤，可用 (1)(2)(3) 分步骤
> - **预置条件**：执行用例前需要准备的配置/环境
> - **预期结果**：与步骤对应的预期结果，可用 预期结果A / 预期结果B 分组
> - **优先级**：High / Medium / Low
> - **测试活动**：仿真 / 现场 / FPGA 等
> - **测试人员**：责任人
> - **备注/建议**：补充说明

## 三、使用说明

1. **测试点分解顺序**：先按 Feature 大类分解 → 再拆分 Sub-Feature → 最后提炼 Test point，并分配测试点编号。
2. **用例与测试点关系**：一个测试用例可覆盖多个测试点，需在「所覆盖测试点编号」字段中完整列出，便于覆盖率统计。
3. **预期结果编写原则**：与 TC 描述中的步骤一一对应，使用「预期结果A / 预期结果B」分组，避免歧义。
4. **命名规范**：
   - 测试点：`tp_<类别缩写>_<对象>_<细分>`，如 `tp_fun_wr_cache_miss`
   - 测试用例：`tc_<对象>_<场景>_<序号>`，如 `tc_ccm_smoke_0`
5. **覆盖标识**：若某测试点暂无用例覆盖，需将「测试点是否被测试用例覆盖」标为 No，并在评审中跟踪闭环。

## 四、与 rtl-flow 的约定

1. 测试用例编号同时是仿真用例名（`+TEST=<测试用例编号>`）。`run_regress.py` 只运行「测试活动」含「仿真」的用例；编号含 `random` 的用例按多个种子运行。
2. 综合、lint、评审等不靠仿真完成的测试点，同样写成测试用例，「测试活动」填实际活动。
3. 需求追溯写在 `07_dv_plan.md` §6：每条 `REQ-xxx` 至少对应一个测试点编号。
4. 新增编号只用小写字母、数字和下划线；需求或继承项目已有编号原样保留，不为统一风格改名。当前解析器识别 `tp_[a-z0-9_]+` / `tc_[a-z0-9_]+`；若原编号不兼容，保留来源并向编排者报告命名 / 入口映射需求，不能让用例被静默漏掉或擅自改名。
5. `check_docs.py` 在 dv 阶段检查：编号不重复，用例引用的测试点已定义，Yes / No 与实际覆盖一致；签核时不允许还有 No。

## 五、测试因子与平台映射

本节合并自 `logic-verify-uvm-tc-gen` v1.2.0 的测试因子指导书；测试点 / 用例字段仍以本文 §一–四为唯一格式。输入导入、用例生成和检查步骤见 [用例生成参考](uvm-testcase-generation.md)。

### 5.1 提取与分类

从规格、接口、寄存器和历史问题提取可能影响行为的因素，先发散、再去重聚合，最后核对取值范围与可观测性。tb-engineer 不采用原指导书中的“读取系统实现”路径，不读 RTL。该方法主要用于功能场景；性能、安全、可靠性等目标还需各自的专门验证依据，不能只靠因子组合证明。

| 因子类型 | 内容 | 取值依据 |
|---|---|---|
| 配置 | 模式、通道、开关、阈值 | 规格合法值、复位值与参数范围 |
| 输入 | 数据、长度、速率、间隔、错误注入 | 接口协议与边界；非法值只用于定义了预期的异常场景 |
| 前提 | 复位 / 初始化状态、队列空满、并发请求 | 由公开操作建立并验证，不访问 DUT 内部状态 |
| 输出 / 检查 | 返回数据、顺序、中断、统计、时延 | 规格规定的外部可观察结果与独立参考模型 |

因子名称清晰且可追溯，取值定义尽量互斥、完整。记录因子间依赖和不合法组合，不强行假设所有因子独立。示例中的通道数 512、包长 60 / 1518 / 9672、CRC 编码等不能作为其他项目的默认值。

### 5.2 因子表与平台操作

可在 `07_dv_plan.md` §3.3 维护下表；细节很多时放 `dv/test_factors.md` 并从 07 引用，不重复维护两份表。

| 测试点 | 因子 / 类型 | 来源 | 值域 / 边界 | 依赖 / 前提 | 平台配置或激励 API | 观测 / 检查点 | 匹配状态与缺口处理 |
|---|---|---|---|---|---|---|---|
| `tp_*` | 规格中的因子名 / 配置、输入、前提、输出 | REQ、规格章节或输入 sheet / 行 | 合法值、边界、异常值 | 组合约束 | 具体 task / 配置字段 / sequence / 寄存器接口 | 对应步骤的可观察预期 | 已匹配 / 未匹配，说明处理依据 |

未匹配项不能静默使用默认值或跳过。优先找规格允许的等价公开接口；缺少配置 / 检查能力时记录受影响的 REQ 和测试点，交由编排者安排补充或澄清。每个生成用例在“TC 描述 / 预置条件”写出组合值和实际操作，在“预期结果”逐步对应，不用相同空泛步骤覆盖所有测试点。

### 5.3 组合与设计方法

| 方法 | 适用情况与约束 |
|---|---|
| 全组合 / DCoT 数据组合 | 有限且关键的因子取值，先排除非法组合；笛卡尔积规模为各因子取值数之积 |
| 正交组合 | 多配置均匀取样；记录采用的组合表及未覆盖的交互，不宣称覆盖全部组合 |
| Pairwise | 覆盖所有合法的两因子取值对；验证实际生成集合的覆盖，用例数取决于因子 / 约束，不套固定 N² 或 N³ |
| 典型值 / 边界值 | 最小、最大、边界内外、典型中间值，随机作为补充 |
| DTT 判定表 / DPT 判定点 | 条件组合、优先级和判定逻辑；独立列出冲突同拍场景 |
| PCT 处理路径 / STT 状态转换 | 多步事务、复位中断、状态迁移 / N-switch；状态以规格可观察行为建立 |

记录选择理由、约束、预计用例数和未覆盖项；随机种子与约束要可复现。需求更新时增量调整因子和关联用例，缺陷闭环补上对应因子 / 边界场景。

### 5.4 覆盖闭环

- 每条 REQ → 至少一个测试点 → 至少一个用例 → 实际激励和检查实现。
- “Yes”只表示该测试点已被用例设计覆盖，不能当作仿真命中或功能通过。
- 动态功能命中由 COVER / 已接入平台的覆盖模型给出，功能通过来自实际运行；代码覆盖与功能覆盖分别记录。
- 非仿真需求继续保留实际测试活动和完成证据；从 BT 表导入时被过滤的行不自动豁免需求。
- G3 提交因子策略、步骤 / 预期、激励实现和未匹配项；正式回归后的结论由编排者记录。
